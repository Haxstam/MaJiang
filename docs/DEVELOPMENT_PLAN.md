- 首版仅实现局域网四人立直麻将。
- 游戏规则参照雀魂；规则保留参数化能力。
- R1–R16 与 B1–B3 已获得用户回答；R8、R9、R16 按用户具体说明确定。细节见规则文档，用户决定优先于外部规则资料。
- 房主客户端内置服务端，其他玩家通过局域网 IP 和端口加入。
- 手写二进制序列化、固定 1024 字节包是项目作者的原有实现，可以保留，也允许在必要时调整。
- 先明确开发规划和实现路径，再修改运行代码。
- 允许清理或重写混乱的旧网络代码；可理解、可验证的原有游戏逻辑优先复用。
- 客户端用公共信息和自身私有信息计算可操作项，提交自己的选择；服务端复用共享规则校验并裁定结果，不要求每阶段下发完整操作列表。

已确认规则与后续牌例验证要求见 [规则与计分](RULES_AND_SCORING.md)。

## 2. 首版产品目标与边界

首个验收模式为四人东南战，保留东风战配置入口。先用简单调试界面验收，再制作正式界面。

首版完成标准：四个客户端能够加入同一房间、准备、开局、完成操作与响应、结算、进入下一局，最终得到一致的点数与排名。

四人准备后由房主点开始。首版包含普通客户端断线后的原座位恢复。断线期间由服务端继续计时并执行默认动作；恢复后接收当前可见快照。房主退出或进程终止时结束房间，不实现房主迁移或服务端重启恢复。

暂不实现公网穿透、自动匹配、账号系统、观战、三人麻将、独立服务器部署、完整回放播放器和美术动画。服务端全量日志为后续排错与回放保留扩展点。

## 3. 重构前的主要结构问题

本节记录迁移前观察，P1/P2已处理的内容见实现记录，不代表当前仍保留这些依赖，也不代表已完成全部规则审计。

- `MainMatchControl.ServerFourMatchInit` 接收 `Dictionary<MatchServer.ClientData, byte[]>`，游戏初始化依赖连接与接收缓存。
- `MainMatchControl` 的客户端初始化直接接收 `Pack`，游戏状态创建依赖具体协议布局。
- `MainMatchControl` 和 `MatchServer` 都有操作校验、响应处理或阶段推进入口，最终应收敛为一个权威推进入口。
- `NetworkControl` 同时容纳连接、拆包、分发、客户端对局状态与调试输入；服务端也混合了传输、房间和规则处理。
- `NetworkStatu` 混合连接状态、房间状态和对局阶段，难以独立管理断线恢复。
- 旧文档的风险列表包含历史问题；部分已有修复记录，必须逐项核对，不能直接视为当前缺陷。

当前工作区已有未提交的代码、场景和文档修改。迁移基线必须包含这些工作区内容，不能仅依赖当前 Git 提交恢复。

## 4. 建议的模块职责

| 模块 | 职责 | 依赖边界 |
| --- | --- | --- |
| 麻将核心 | 牌与手牌、规则参数、完整对局状态、合法操作、响应裁定、阶段推进与结算 | 不引用 Socket、Pack、连接对象、MonoBehaviour 或 Unity 时间 |
| 对局服务 | 将已识别玩家的请求交给核心，管理请求编号、阶段期限、超时与断线默认操作 | 依赖核心，不处理字节偏移 |
| 房间服务 | 加入、离开、座位、准备、配置、开局与重连会话 | 不计算役种或直接修改手牌 |
| 网络协议与传输 | 二进制编解码、1024 字节帧、连接生命周期、读取与发送 | 不裁定游戏规则 |
| 客户端状态 | 安装房间状态与自身可见对局快照，调用共享规则计算操作选项，提交选择，通知界面 | 不持有其他人的暗手或未公开牌山，不自行推进权威对局 |
| Unity 表现 | 输入、显示、场景生命周期与调试工具 | 通过服务接口和客户端状态工作 |

这些边界不要求立即建立多个程序集或深层命名空间。先确保类之间的依赖明确，按现有 Allman 与 XML 注释风格实现。

核心接口应表达“创建对局、查询合法操作、提交命令、查询状态与结果”。客户端身份由服务端连接会话确定，命令中自报的玩家编号不作为身份依据。

### 4.1 本地操作计算与服务端校验

客户端计算操作菜单，服务端检查提交操作，二者使用同一份共享规则代码，避免分别维护两套吃碰杠、振听和役判断。

- 客户端查询仅接收公共状态、自己的手牌、自己的振听/立直等标记及当前响应上下文，不读取完整服务端状态。
- 服务端从权威状态生成对应玩家的规则查询视图，独立校验动作与具体牌参数；不信任客户端声称“可以荣和/可以杠”。
- 网络传输以状态和玩家选择为主，默认不下发所有合法操作及组合。
- 本地选项重算不改变手牌、供托、振听或阶段。选择提交后等待服务端结果，避免本地提前出牌导致状态分叉。
- 服务端保留对合法响应者和超时的判断，不能根据客户端没有显示按钮就认定玩家没有和牌机会。
- 需验证相同可见状态在两端生成相同操作，尤其是重连后不能丢失同巡振听、立直后见逃或当前已答复状态。

## 5. 单一权威推进流程

建议仅有以下流程能够改变权威对局：

1. 对局服务收到请求或服务端超时事件。
2. 根据会话找到固定座位，检查本局与阶段编号。
3. 麻将核心判断命令是否合法。
4. 核心执行状态变化，并产生明确的裁定结果和领域事件。
5. 对局服务递增状态版本、保存日志。
6. 根据各玩家可见范围生成裁定日志并下发；初始化或无法补齐时生成检查点。

阶段至少明确区分：本局初始化、当前玩家操作、舍牌响应、抢杠响应、结算、本局结束和整场结束。响应阶段收集所有有关玩家的答复或等待期限届满后统一裁定，避免按网络到达先后决定多人荣和。

规则中的立直成立、加杠成立、开杠宝牌、岭上摸牌和特殊流局应有明确触发时点，不能通过一条宽泛的“执行动作”路径提前全部生效。

已确认的杠宝牌顺序：暗杠摸岭上牌时翻；大明杠/加杠摸岭上后舍牌时翻。再次开杠时立即翻前一次待翻的指示牌。因此当前大明杠/加杠的岭上和牌不计它尚未翻开的新杠宝牌，暗杠岭上和牌计入已翻开的新指示牌。待翻状态必须显式保存在核心中，结算只使用实际已公开的指示牌。

计时由服务端决定；核心接收显式超时命令，测试可使用虚拟时间，无需等待真实秒数。

## 6. 建议的同步模型

### 6.1 正常走日志，检查点用于初始化和恢复

2026-10-24根据作者对原设计的补充，采用离散裁定日志作为正常同步主路径。每条日志记录动作、阶段与私有裁定状态及变化的牌区；各接收者看到同序号的可见版本。初始化、重连、超过补齐窗口或本地状态损坏时发送当前可见检查点。详见 [可见日志同步](MATCH_SYNCHRONIZATION.md)。

客户端安装检查点后按序应用其后的裁定增量，不再次裁定规则。重复不重放、缺号请求补齐；无法补齐则检查点兜底。客户端仍根据重建状态查询操作菜单。服务端单调时钟通过心跳校准，期限在日志中明确，不为每帧流逝写日志。

一次快照至少包含：

- 对局 ID、本局 ID、状态版本、当前阶段 ID。
- 玩家公开档案、座位、点数、连接状态、局数、本场和供托。
- 牌河、副露、已公开宝牌指示牌、立直等公开标记、剩余可摸牌数。
- 接收者自己的手牌与摸牌、其他玩家的手牌张数。
- 当前操作人、舍牌或抢杠目标、事件上下文、接收者本阶段是否已经答复，以及服务端期限信息。
- 接收者自己的振听、立直等私有规则状态和当前操作限制；仅发送计算所需状态，不发送其他玩家私有标记。
- 已公开杠宝牌数量及待翻指示牌的公开事件状态；不得提前泄露待翻牌面。
- 本局结算时按规则允许公开的手牌、里宝牌、役种与支付结果。

未公开的里宝牌、其他玩家暗手、完整牌山、可推导牌山的随机种子不得进入普通快照。

动作仍供UI表现与排错使用。服务端权威日志记录最终裁定；客户端的可见投影由检查点和有序日志确定。P3a已实现本局完整记录、网络最近512条窗口及每批最多16条，常规更新不发送完整检查点。

### 6.2 请求与版本

建议每条玩家请求携带：对局 ID、本局 ID、阶段 ID、会话内请求编号和具体动作参数。

- 重复请求返回已有处理结果，不重复执行。
- 旧阶段或旧本局请求返回过期结果及当前状态。
- 使用阶段 ID 区分有效期；不能仅因其他玩家在同一响应窗口答复导致状态版本变化，就拒绝本阶段仍有效的答复。
- 旧阶段、旧本局、身份不匹配、重复或已答复请求不消费当前操作机会，不因它们为当前阶段生成跳过或舍牌。
- 对当前仍待答复玩家，本地状态异常导致的非法鸣牌/荣和响应按跳过处理；超时也按跳过处理。若服务端判断其本可荣和，按选定规则更新见逃振听；不是每次跳过都产生振听。
- 摸牌后默认摸切；鸣牌后按明确且可测试的排序选择合法舍牌，禁止食替等限制仍须遵守。自己回合需要舍牌时不能用“跳过”无限阻塞牌局；有效当前阶段的非法请求按此默认舍牌路径处理。
- 跳过或默认操作也写入相应裁定结果，返回原因并同步状态，不重置思考时间。

上述非法响应语义依据用户对 B3 的后续说明，取代早期“所有非法请求都只拒绝并等到超时”的提案。R14 中的手动和牌与见逃规则仍适用。

具体请求编号缓存、版本数值类型和溢出处理在协议实现前固定。

## 7. 二进制协议与传输

建议保留 TCP、手写二进制与固定 1024 字节物理帧。它们足够支持四人局域网麻将，现阶段没有仅为更换技术而迁移 JSON 或第三方联网框架的必要。

保留这些技术不等于继续兼容旧 payload。建议定义新协议版本，明确拒绝不兼容的旧客户端，统一更新两端。

实现约束：

- 一次 Socket 读取可能不足一帧，也可能包含多帧；按固定长度累计解析。
- 包头/尾在规定偏移校验，不通过搜索 payload 内首次出现的包尾来决定帧边界。二进制负载本身可能含有同样的字节序列。
- 对错误帧、未知消息、过长字段和非法计数给出确定处理方式；边界错误时关闭连接，重新连接时从明确帧边界开始。
- 固定字节序、UTF-8 字节长度上限、列表显式计数和空值标记；不以 `false` 或有效的牌值充当列表结束标记。
- 单一消息可以包含多个物理帧。快照超过一帧时使用通用分片，带消息编号、分片序号、分片总数和总长度；同一快照全部验证完整后一次性安装。
- 对消息总长度、分片数、组装数量与组装期限设上限，不能因列表变长而截断快照。
- 已移除旧MD5字段，当前帧v5使用覆盖整帧的CRC-32；相对v4增加结算结果和换局期限，拒绝旧客户端。具体偏移见 [当前协议](NETWORK_PROTOCOL.md)。
- 每个连接仅一个读取任务和一个顺序发送通道；收包与发包队列有明确上限。
- 后台任务只处理传输和数据，服务端命令按队列在同一执行上下文依次处理；Unity 对象及界面更新留在主线程。
- 正确识别 EOF、读取异常、连接超时和取消；关闭服务端、离开场景后释放监听器、连接与后台任务。

消息分为：协议握手、加入/恢复会话、房间请求与状态、动作请求与结果、对局快照、心跳与关闭原因。具体字段与 offset 在实施协议步骤时记录，不继续叠加旧 `SignalType` 和 ACK 特例。

P2已实现房间消息、完整消息分片和会话；P3a已实现可见检查点、日志、确认、补齐请求与阶段时钟；P3b已接入玩家动作、GUID去重、响应裁定及长考/超时。房间版本、帧序号、日志序号、局代数和玩家命令编号分别管理。

## 8. 身份、断线与房主

建议由服务端分配房间内玩家 ID 和随机恢复令牌，显示名称仅用于显示，允许同名。初次加入后客户端保存令牌；恢复连接时验证令牌并重新绑定原座位，旧连接失效。

这只是房间会话，不引入账号系统。令牌不得写入普通调试日志。会话仅在房间生命周期内有效。

- 房间未开局时，离开或清退玩家后可以补位。
- 开局后保留座位与对局状态，断线玩家按服务端计时默认操作，禁止其他新玩家直接顶替。
- 重连后发送当前阶段的完整可见状态，不重置思考时间。
- 房主玩家的客户端连接可以恢复；房主服务端关闭则整个房间结束。
- 首版手动输入 IP 与端口，不加入局域网自动发现作为前置要求。

## 10. 最小验证集合

- 规则核心：普通牌型、七对子、国士、无役但有宝牌、不同拆分取最高合法得点、振听、立直后操作、多人荣和、杠相关响应与流局。
- 本地选项：相同玩家视图在客户端和服务端查询结果一致；快照恢复振听与已答复状态；非法当前响应按跳过，旧阶段请求不跳过新阶段。
- 杠宝牌：暗杠岭上计新宝牌，大明杠/加杠岭上不计尚未翻开的新宝牌，舍牌开宝牌，连续开杠公开前一待翻指示牌；抢杠中断时不先完成本次杠和岭上摸牌。
- 状态机：响应顺序不同但结果相同；超时与收到请求的边界有固定裁定；供托不重复扣除；本局切换后拒绝旧消息。
- 协议：每种消息往返编解码；非零 offset；边界字段；空列表与 false；多帧和不足一帧；快照分片完整性与有界组装。
- 信息边界：逐玩家检查真实发送数据，不仅检查客户端 UI；普通快照中不出现暗手、未公开里宝牌或完整牌山。
- 恢复：普通客户端在自己操作、等待鸣牌、结算或切局期间断线并恢复；重复提交恢复前的请求不会改变结果。
- Unity：房主与三个普通客户端连接，同机多进程及不同局域网机器；检查实际场景引用、输入、主线程更新与退出行为。

核心与协议测试尽量无需 Unity 场景。具体测试工程形式在 P1 根据现有项目引用选择，避免为测试引入无关框架。

## 11. 旧代码处理

- 迁移前逐个分类为领域模型、可保留规则、待修正规则、协议旧版、重复控制逻辑或占位文件。
- 不用当前提交覆盖未提交的场景和源代码。
- 新模块达到对应验收门槛后，在同一迁移步骤中删除或收窄旧入口，最终仅保留一条对局推进路径。
- `Network Scripts/Client`、`Server`、`PackCoder` 等占位文件确认无场景引用后可删除；同时处理对应 `.meta`。
- 修改或替换 Unity 脚本时检查 `.meta`、场景、Inspector 引用和序列化字段；需要编辑器操作时明确列出操作及验证方式。
- 不因“已有实现”跳过规则验证，也不因某个方法难懂就连带删除未经检查的领域算法。
