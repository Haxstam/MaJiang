# 玩家可见日志同步

> 2026-10-24：P3/P4已接入操作和整场结算。正常推进使用日志，初始化与恢复使用可见检查点。共享菜单见 [状态机](STATE_MACHINE.md)，结算与换局见 [计分整场](SCORING_AND_MATCH.md)。

## 1. 与原设计的关系

本轮参考原`ApplyActionLog`、`CreateVisibleAction`和差量请求实现，保留以下思路：

- 服务端保存完整权威牌局，只有服务端记录已裁定结果。
- 本局日志从0开始，客户端初始最后已应用序号为-1。
- 客户端按序重建可见状态，重复日志不再次应用，缺号请求补齐。
- 摸牌玩家本人获知牌面，其他玩家只获知谁摸牌及手牌张数变化。

主要补强：日志记录动作及其裁定增量，而不是收到动作后在客户端再裁定一次规则。阶段、振听、已答复与计时依据也明确传输。这样保留可重放性，同时避免两端对一条Skip推断出不同的私有状态。

这是对先前“每步完整快照”提案的调整；当前正常同步主路径已经改为日志。

## 2. 权威、日志与检查点

`MatchJournal`持有权威核心的引用。规则服务先完成合法性检查和状态变化，再调用`RecordAppliedAction`；日志层不自行判断荣和、鸣牌或替玩家选择动作。

每条裁定产生四份同序号的可见记录。服务端保留本局完整记录；网络提供最近512条的补齐窗口，单批最多16条。超过窗口、序号异常、客户端状态损坏或主动完整恢复时发送当前检查点。每局最多4096条，防止程序错误导致无界记录。

建立本局基线时序号为-1。当前开局流程先发13张手牌并公开第一张宝牌指示牌，再记录庄家首摸为第0条；客户端初次加入牌局直接安装最新可见检查点，第0条仍保留以便从基线重放。

检查点相当于“应用到某一日志位置后的状态”。普通日志不重复整个牌局，只传变化的区域和小型裁定状态。

## 3. 信息边界

每个客户端的状态包含：

- 四家公开档案、点数、牌河、副露、已公开宝牌、立直等公共标记及暗手张数。
- 自己的暗手与摸牌；自己的振听标记、已答复状态、长考余量。
- 对局/本局标识、日志序号、阶段编号、阶段类型、当前玩家、阶段期限和服务器时钟采样。
- 待翻杠宝牌的数量，不包含待翻牌面。
- 细分操作窗口、响应来源/目标、待确认立直座位、本人食替限制、结束原因及和牌者位图。

不编码完整牌山、王牌、随机种子、其他玩家未公开暗手或未公开里宝牌。P5已移除牌局投影的里牌空字段；里指示牌只存在于允许公开的独立结算中，不覆盖其他玩家的新局私有手牌。

摸牌日志在发给其他玩家时清空目标牌和涉及牌；可见状态中的`CurrentTile`也必须遮蔽。舍牌公共上下文取自实际舍牌动作，不能直接复制核心里可能仍留存的上一张私有摸牌。Skip不携带原非法选择的牌。

日志与检查点复制可变列表、动作和更新字节；外部修改返回对象不会改写已发布日志。客户端只获得自己的可见投影；房主本地服务端持有完整状态属于运行模式本身。

## 4. 增量内容与客户端应用

每条记录包含：

1. 本局日志序号。
2. 可选的裁定动作：动作类型、玩家、来源、公开涉及牌和目标牌。null动作表示阶段或私有裁定变化，不等同于玩家Skip。
3. 当前公共标记与接收者自己的裁定/计时状态。
4. 各座位牌河是否变化；变化时附该座位完整牌河。
5. 各座位副露是否变化；变化时附该座位完整副露列表。
6. 已公开宝牌是否变化。
7. 本人暗手/摸牌是否变化；变化时附本人新手牌。

牌河、手牌、面子均有显式计数，不复用旧512字节公共状态或0值结束标记，也不固定每人24张牌河。

客户端先在临时状态应用完整批次，检查序号与本人手牌张数等约束后一次安装。缺号或坏增量不会安装半个批次；本地状态无法继续演算时请求检查点。正常应用不再调用旧`MainMatchControl.ActionDeduce`，动作仍可供UI动画、排错和未来回放使用。

本地计算可用操作属于共享规则查询职责；它读取已重建的公共信息和本人手牌，不改变权威状态，也不要求服务端每次发送完整操作菜单。`GetAvailableActions`已接入`MatchActionRules`，客户端`AvailableCommands`将选择绑定当前本局/窗口后供提交。

## 5. 局隔离与恢复

- `MatchId`标识整场，`RoundId`标识具体本场，`RoundGeneration`在同一场内单调递增。
- 每个新本场使用新RoundId，序号重新从-1基线开始。
- 旧本场日志或检查点不能回滚新本场。相同局代数却不同RoundId属于冲突。
- 客户端只确认已经应用的序号。补齐请求携带完整局身份及最后已应用序号；服务端从下一条发送。
- 明确请求完整恢复或新连接的首次检查点，允许校正同一局中被本地错误写成“未来”的序号；普通晚到的旧检查点仍不回滚当前状态。
- 重连通过P2恢复令牌绑定原座位，发送该座位当前检查点。期限、本人振听、已答复与时间余量由服务端恢复，不按“重新连接”重置。
- 当前无缺失日志的同步请求也返回空批次，避免客户端一直等待响应。

帧序号、房间版本、日志序号、局代数与玩家命令GUID分别管理。

## 6. 时间

阶段日志携带服务端进程单调时钟上的绝对期限。服务端每秒心跳附带单调时钟采样，客户端用本地经过时间显示倒计时；旧日志时间采样不允许让时钟回退。不会把每帧的时间流逝写成日志。

P3b已实现长考消耗和超时默认动作。每个接收者只收到自己的期限，无操作机会时为0；有选择者每窗口5秒加本局剩余长考。先答复者长考冻结，剩余人继续计时。快照按当前时钟采样，不因重连退还时间；正常流逝不生成逐帧日志。

## 7. 网络格式

当前帧版本为5，新增公开结算与下一局期限，拒绝旧客户端。物理帧布局仍是32字节头、984字节负载、8字节尾。

| 类型 | 方向 | 负载 |
| --- | --- | --- |
| MatchSnapshot=11 | 服务端→客户端 | 局身份、序号、接收座位、规则副本、四家名字、裁定状态、四家牌河/副露、宝牌、本人暗手与摸牌 |
| MatchLog=12 | 服务端→客户端 | MatchId、RoundId、int局代数、long最新序号、byte记录数，再逐条写long序号、可选动作、带int长度的更新数据 |
| MatchAck=13 | 客户端→服务端 | MatchId、RoundId、int局代数、long最后已应用序号 |
| RequestMatchSync=14 | 客户端→服务端 | 同上，再加Bool强制检查点 |

身份头的两种Guid各16字节；整数统一小端。规则副本暂复用现有16字节MatchSettingData编码；完整参数化规则预设后续扩展时需要更新版本。具体字段实现见`MatchSyncCodec`。

固定1024字节帧意味着较小的逻辑消息依然至少占一帧。当前日志方案的主要收益是可重放、缺号修复和明确裁定，不声称每个操作在网络上一定比小检查点少占字节。
